# Design

## Context

见 `proposal.md — Why`。这里只记录影响技术方案的事实。

**参考实现**：`D:\jarvis\link_chat` 是一个 Go + `github.com/gdamore/tcell/v2` 的终端聊天客户端，它的 `pkg/tui/theme` 定义了 `ink` / `paper` 两套语义化调色板（`Bg`、`Surface`、`Text`、`Accent`、`Border` 等 16 个令牌），`pkg/tui/layout` 定义了以 `GutterX = 2` 为基础的间距网格与 `go-runewidth` 的宽度测量策略，`pkg/tui/widget` 提供 `Rect` / `Canvas` 这类无状态绘制原语。这套语言适合"信息型"界面：文字、列表、分隔线。

本工程需要的是"动作型"界面：连续的空间、逐帧变化的位置、瞬时反馈。两者共享的只有一部分——取色与终端能力探测的方式、对 ASCII 降级的坚持、以及对"不靠颜色单独传达信息"的原则。渲染层必须重写，主题令牌可以借用语义命名但要扩展游戏专用的类别。

**约束**

- 终端没有帧缓冲 API，只有"设置某个字符单元的字符 + 前景色 + 背景色"。一次 `Show()` 就提交一帧，tcell 内部做差量。
- 终端字符单元不是正方形，常见宽高比约 1:2（等宽字体更接近 1:2.2）。
- 终端键盘事件并发能力有限，部分组合键会被终端或输入法吞掉；`Shift` + 方向键在 Windows Terminal 下通常可用，但在部分 conhost / tmux 配置下不可靠。
- 模拟必须在不同机器、不同刷新率下表现一致，否则手感无法校准。

## Goals / Non-Goals

**Goals:**

- 物理常量与 SMB 原版的逐帧数值对齐，手感可被有原版经验的玩家辨认。
- 模拟完全确定性：整数定点数，固定步长，同输入同结果。
- 渲染与模拟彻底解耦，渲染频率可调（默认 30 fps），模拟恒为 60 Hz。
- 一份关卡数据可被修改、校验、并在不重新编译的前提下生效。
- 终端能力降级有明确边界：真彩色 / 256 色 / 单色，Unicode / ASCII。

**Non-Goals:**

- 不追求像素级复刻原版贴图。只保证剪影与比例可辨识。
- 不做可扩展的多关卡系统，本变更只交付 1-1；但关卡类型与加载入口要留出加关的空间。
- 不做网络、回放、录像存档。
- 不做声音。
- 不在本变更内支持游戏手柄。

## Decisions

### 决策 1：模拟层使用整数定点数，不使用浮点

**选择**：位置与速度以 `int32` 表示，单位为 1/256 个"游戏单位"，1 个瓦片 = 16 游戏单位 × 256 = 4096 个定点单位。所有常量以原版的"每帧像素 × 16"为基准推导。

**理由**：
- 原版 SMB 本身就是定点数实现，它的手感来自特定帧数上的特定整数增量。用浮点复现会引入舍入差异，且不同平台（x86 SSE / ARM NEON）的浮点结果不保证逐位一致，破坏可复现性。
- 整数运算在三轴（位置、速度、重力）上的溢出行为明确，便于推理。
- 可以在测试里直接比较位置是否"逐位相等"，而不需要 epsilon。

**备选**：`float64` 更易读，但会牺牲确定性，并让"同样的输入在不同机器上跳到不同高度"成为可能。放弃。`float32` 同理。

**代价**：常量表需要手算成定点，可读性差。缓解：常量的定义处保留"原版每帧像素"的注释，用一个 `px(v float64) int32` 的编译期转换辅助函数写常量。

### 决策 2：固定步长 1/60 秒，追赶步数上限 5

**选择**：主循环用累加器（accumulator）模型：每帧把墙钟增量累加进 `acc`，当 `acc >= step` 时执行一步并从 `acc` 扣除。单帧最多执行 5 步，超出部分直接丢弃并把 `acc` 清零。

**理由**：
- 60 Hz 与原版一致，所有常量可以直接使用。
- 上限保证终端挂起后恢复不会出现"快进几十秒"的雪崩。
- 丢弃而不是慢放，是最不容易让玩家困惑的选择：时间跳了，但画面是连续的。

**备选**：可变步长 + 时间缩放——会让物理不稳定（大步长下高速物体穿模），且破坏确定性。放弃。每个 Tick 回调一次并强制固定——在某些终端上 `Show()` 的阻塞会让实际步长漂移，同样破坏手感。放弃。

**渲染频率**：默认 30 fps（每 2 个模拟步渲染一次），可由 `-fps` 覆盖。渲染与模拟各自有独立的节拍器。

### 决策 3：碰撞采用逐轴扫掠 + 子像素位置

**选择**：每个实体在一步内先按 `vx` 移动，检测水平重叠并解算；再按 `vy` 移动，检测垂直重叠并解算。检测时用 AABB 与瓦片网格求交，起点到终点的整个扫掠区间都参与。

**理由**：
- 单次任意方向求解会让"斜着落到平台边缘"被误判成侧面撞击，这是横版跳跃游戏最常见的手感 bug。
- 逐轴分离后，每个轴只需要处理"是否有重叠"和"贴到哪一侧"，逻辑简单且可单测。
- 速度上限（约 6 游戏单位/步）小于一个瓦片（16 单位），单步内不会跨过整块瓦片；但为安全起见仍按扫掠区间取瓦片，而不是只取终点所在瓦片。

**备选**：仅采样终点瓦片——高速时会穿墙。放弃。连续碰撞检测（CCD）的精确解——对本游戏没有必要，且会引入浮点。

### 决策 4：实体用具体结构体 + 统一接口，不做 ECS

**选择**：`Player`、`Enemy`（含 `kind` 区分蘑菇怪/乌龟/壳）、`Item`、`Brick`、`Coin`、`Particle` 各自是具体结构体。它们实现一个极小的接口（`ID()`、`Update()`、`Bounds()`、`Draw()`）。世界持有一个按出生序号排序的切片。

**理由**：
- 本游戏实体种类少于 10，且没有"组合无限属性"的需求。ECS 的收益不会覆盖它的认知成本。
- 确定性要求更新顺序固定。按出生序号排序的切片是最简单可靠的定序方式。
- 具体结构体可以在测试里直接构造与断言字段，不需要绕过 ECS 抽象。

**备选**：ECS——在这里是过度设计。接口化但用 map 存储——不可预测的遍历顺序会破坏确定性，必须额外排序，反而更麻烦。放弃。

### 决策 5：关卡用声明式 JSON，编译期内嵌

**选择**：关卡是 `level/*.json`，包含瓦片层的游程编码（RLE）行、实体列表、方块内容表、出生点、旗杆与边界。用 `go:embed` 编译进二进制，同时支持 `-level <path>` 从磁盘覆盖加载。

**理由**：
- RLE 让 1-1 的 200+ 列地形在文件里保持可读（一行一行写 200 个字符也行，但空格密集的关卡会产生大量冗余）。
- `go:embed` 保证单二进制分发；`-level` 支持不重新编译就改关卡，满足规格里"数据可独立修改"的要求。
- 校验在加载时完成（坐标越界、缺出生点、方块内容引用不存在），失败时报出行列。

**备选**：用 Go 代码描述关卡——违反"数据不含代码"，且改关卡要重新编译。放弃。纯文本字符画（每行一串 `.`/`#`/`?`）——可读但在地形高度变化时列宽难以人工对齐，且无法表达实体参数。放弃，但 RLE 的符号表借鉴了字符画的直观性。

### 决策 6：渲染走"虚拟像素 → 半块字符"两段式

**选择**：

```
游戏单位 (16/瓦片)
   │  整数除 (artPxPerTile 缩放)
   ▼
美术像素 (8 art px / 瓦片)
   │  × k  (k = 1 或 2, 由 -scale 决定)
   ▼
虚拟像素 (vp)
   │  纵向两两配对 → 上像素 = 前景色, 下像素 = 背景色, 字符 = '▀'
   ▼
终端字符单元
```

纵向配对时：
- 上下像素同色 → 用空格 + 背景色
- 上下不同 → `▀`，前景 = 上，背景 = 下
- ASCII 降级 → 只取上半像素，用 `#`/`.`/`=` 等字符表现层次，纵向分辨率减半

**理由**：
- 半块字符是终端里唯一的"免费提升分辨率"手段，能把有效纵向分辨率翻倍，让 1:2 的字符格变成接近 1:1 的像素格。
- 两段式缩放把"美术分辨率"与"显示分辨率"解耦：同一份 8×8 的瓦片美术，在 `-scale 1` 和 `-scale 2` 下都能正确绘制，不需要准备两套素材。
- 先合成到虚拟缓冲再整体转换，保证"后画的盖住先画的"这一绘制顺序语义。

**备选**：直接逐实体写 tcell 单元——无法表达半像素，且无法做统一的绘制顺序。放弃。用六线符（Braille）——纵向 4 倍分辨率但需要单色，且色块表现差。放弃。

**美术分辨率与缩放**：

美术母版按 1 瓦片 = **16 像素**绘制（与原版一致）：小马里奥 16×16，大马里奥 16×32。这是角色可辨认的下限——8×8 的空间装不下帽檐、鼻子、胡子与背带裤，只能得到色块。早期方案里的"每瓦片 8 像素"已废弃。

显示时按终端宽度选择"每瓦片占几个字符单元"：

| 模式 | 每瓦片列 | 每瓦片行 | 160 列可见 | 120 列可见 | 说明 |
|---|---|---|---|---|---|
| `native` | 16 | 8 | 10 × 6.2 | 7.5 × 5 | 1 美术像素 = 1 字符列，最清晰 |
| `small` | 12 | 6 | 13 × 8.3 | 10 × 6.7 | 母版按 16→12 降采样，视野更大但角色变糊 |

`-scale auto`（默认）在终端宽度 ≥ 160 列时用 `native`，否则用 `small`。

**纵向视野只有 6–7 瓦片**，而 1-1 的旗杆高 9 瓦片，因此相机 MUST 支持垂直跟随：以玩家为中心，上下各留 1 瓦片死区，超出即滚动；靠近地面时相机底边贴住地面线。这一点取代了原先"不做垂直滚动"的假设。

### 决策 7：物理常量对齐原版，集中在单一表里

**选择**：所有手感参数（加速度、摩擦、滑铲减速度、跳跃初速、重力、速度上限、空中控制系数、可变跳跃截断比例）集中定义在 `pkg/game/tuning.go` 的一张表里，每一项注释原版对应的每帧像素值。

**关键基准**（原版 16px 瓦片 / 60Hz）：

- 行走上限 ≈ 1.5625 px/帧 = 25 单位/秒
- 奔跑上限 ≈ 2.5 px/帧 = 40 单位/秒
- 地面加速度 ≈ 0.0371 px/帧²；摩擦 ≈ 0.0508 px/帧²；滑铲减速度 ≈ 0.1016 px/帧²
- 起跳初速 ≈ -4.0 px/帧（受水平速度小幅加成）
- 下落重力 ≈ 0.4375 px/帧²；上升重力 ≈ 0.1875 px/帧²（上升更轻，形成原版的"飘"）
- 长按跳跃时上升速度在若干帧后封顶，短按则直接截断

**理由**：这些不是调出来的，是从原版行为反推的。把它们写在一处并注明来源，后续调参才有基准，也避免某次"随手改好看一点"污染手感。

**备选**：凭感觉调参——会得到一个"能玩但不像马里奥"的游戏。放弃。

### 决策 8：渲染层自带最小化的主题，不复用 link_chat 的包

**选择**：`pkg/render/theme` 重新定义游戏专用令牌：`Sky`、`Ground`、`GroundEdge`、`Brick`、`BrickEdge`、`Question`、`QuestionUsed`、`Coin`、`PlayerBody`、`PlayerAccent`、`EnemyBody`、`EnemyAccent`、`Item`、`HudText`、`HudMuted`、`Backdrop`。同时保留 link_chat 的 `ink` / `paper` 两套基底，游戏令牌从基底派生（例如 `Brick` 取自基底的 `Warning`，`Ground` 取自 `SurfaceAlt`）。

**理由**：
- 直接 `import "link-chat/pkg/tui/theme"` 会把一个本地兄弟工程变成构建依赖，跨机器不可复现。
- 但视觉语言应当一致：同样的低饱和背景、同样的强调色克制原则。派生关系把这条约束写进了代码。
- 终端能力探测（真彩色 / 256 / 单色）的逻辑与 link_chat 的实现思路相同，直接照搬其 `ColorCapacity` 三档模型。

**备选**：把 link_chat 的 theme 包复制过来——会带上聊天专用的 `SelectedBg`、`SurfaceAlt` 等无用令牌，且后续两边演进会分叉。放弃。

### 决策 9：输入采样用"队列 + 状态位"双层结构

**选择**：终端事件进入队列；每个模拟步开始时：
1. 把队列里本步的所有事件折叠成边沿位（`PressedJump`、`ReleasedJump` 等）与状态位（`HeldLeft`、`HeldRun` 等）的快照；
2. 模拟读快照；
3. 步结束后清空边沿位。

**理由**：
- 规格要求"同一帧内两次按下只算一次"。折叠成位自然满足。
- 状态位用快照而不是直接读终端状态，保证一个渲染帧内多个模拟步看到的输入一致（否则第二个步可能看到"已经松开"，导致跳跃高度抖动）。
- 键位表把物理键映射到动作，逻辑层只看到动作。

**备选**：让模拟直接查询终端事件——会把 I/O 时序带进模拟，破坏确定性。放弃。

### 决策 10：最高分存档放在用户配置目录，写入失败不阻断

**选择**：`os.UserConfigDir()/super-mario/save.json`，内容为 `{"highScore": 12345, "version": 1}`。加载失败（不存在、损坏、无权限）一律回落到默认值，并在首次失败时于标题界面底部给一行非阻断提示。写入失败同样只提示，不中断。

**理由**：规格明确要求存档问题不能阻止游戏启动。独立目录避免污染工程目录。

**备选**：写在 `%APPDATA%` 硬编码路径——跨平台不可移植，且 `os.UserConfigDir` 在三个平台上已经给出正确位置。放弃。

### 决策 11：渲染只在脏区域提交，并做周期性全量重绘

**选择**：虚拟缓冲转换出的字符层与上一帧的字符层做逐单元比较，只把不同的单元通过 `SetContent` 写入 tcell；tcell 的 `Show()` 本身也做差量，两者叠加。每 60 帧或收到 `Resize` / 焦点恢复事件时强制全量重绘一次。

**理由**：终端在高频全屏重绘时，尤其在 Windows conhost 上，会出现明显的闪烁与输入延迟。周期性全量重绘防御终端侧的差量状态漂移（例如终端自身清屏、tmux 重绘）。

**备选**：完全信任 tcell 的差量——在某些终端模拟器切换后会出现残影。放弃。

## Risks / Trade-offs

**[终端刷新率不足 30 fps → 动作迟滞]** → 渲染与模拟解耦，模拟始终保持 60 Hz，画面掉帧不会改变物理。同时把渲染默认降到 30 fps，并允许 `-fps` 调到 15。差量刷新减少每次 `Show()` 的工作量。

**[半块字符在某些等宽字体下出现缝隙或颜色渗漏]** → 默认使用 `▀`；启动时探测 `TERM` / 平台，对已知有问题的组合（例如部分 conhost 字体）回落到整块 `█` + 单色，接受纵向分辨率减半。`-scale 1` 下纵向仍有 10 瓦片，可玩。

**[Windows 终端吞掉 Shift 组合键]** → "跑"动作同时绑定 `shift` 与 `x`；另外提供粘滞跑模式（按一次 `X` 锁定奔跑，再按一次解锁），在 `?` 帮助里说明。

**[定点常量手算错误导致手感偏差]** → 在 `tuning.go` 的每一行保留原版 `px/帧` 注释，并在测试中断言关键派生值：例如"从静止按住奔跑，达到速度上限所需帧数"应落在原版的帧数区间内。数值错误会在测试里暴露，而不是等到玩的时候才感觉不对。

**[关卡 JSON 与代码内的瓦片符号表不一致]** → 符号表只定义一次（`level` 包内的 const），加载器用它解析；测试用内嵌的 1-1 做一次完整往返解析，确保每个符号都能被识别。

**[相机单向滚动 + 玩家后退，可能出现玩家被推着走的观感]** → 只在玩家越过屏幕中部阈值时前推；玩家越过左边缘时由关卡边界阻挡。相机不做回拉，这是原版行为，也是关卡设计的前提。

**[变大时在低矮空间内卡住]** → 变大的碰撞体增长从下往上依次求解：先尝试向上扩展（头顶有空间），失败则向下扩展（脚下有空间），都失败则保持小形态并消耗道具但不生效。规格已覆盖此场景。

## Migration Plan

新工程，无迁移。首次运行即创建存档目录。

## Open Questions

无。影响规格、方案或任务拆分的不确定项已在上述决策中解决；纯视觉微调（具体色值、精灵造型）可在实现阶段直接迭代，不改变契约。
